### Touch panel control added (branch: `touch-panel-control`)
- New XPT2046 resistive touch layer over the ILI9341 screen: on-screen buttons for Fan −/+, Heat −/+, and STOP (`src/touch.h`, `src/touch.cpp`), wired into the existing `enqueueStateRequest()`/`processStateQueue()` arbitration as a new `SOURCE_TOUCH` ([model.h](src/model.h)), except STOP which calls `eStop()` directly, bypassing the queue entirely (deliberate — immediate local emergency stop shouldn't wait on arbitration).
- **Pin discovery**: initially guessed the touch controller shared the display's SPI bus (`TFT_SCLK/MOSI/MISO`) with only its own `TOUCH_CS`, copying the pattern that worked for the display pins. Wrong — the on-screen "touched" indicator stayed permanently true even with no finger on the panel (floating/garbage SPI reads). Found a blog post describing this exact board (its listed TFT pins matched ours exactly, confirming it's the same board) stating the touch controller is wired to a **completely separate SPI bus**: `TOUCH_CS=1, TOUCH_CLK=42, TOUCH_MOSI=2, TOUCH_MISO=41` ([display.h](src/display.h)). Since the `XPT2046_Touchscreen` library always talks to the global `SPI` object (no way to inject a different `SPIClass`), fixed by giving the **display** its own dedicated `SPIClass tftSPI(HSPI)` instead ([display.cpp](src/display.cpp)) and reserving the global `SPI` for touch (`touch.cpp`'s `touchInit()`).
- **Coordinate calibration**: default XPT2046 raw ADC range (200–3900) was a generic placeholder. Measured actual 4-corner raw values on hardware and found the raw X/Y axes are **not swapped** (original code guessed a swap — wrong) but **both run inverted** relative to screen coordinates. Recalibrated `TS_MINX/MAXX/MINY/MAXY` in `touch.cpp` from real corner readings; confirmed via a temporary on-screen raw/mapped-coordinate readout (reused the status text area, since WebSerial requires a WiFi connection mid-hardware-test) that taps on STOP and Fan+ land inside their correct button rectangles.
- **Verified on real hardware**: Fan+ button changes `F:` by the expected step; STOP immediately forces `H:0, F:100` regardless of queue state, bypassing arbitration as designed.
- Emergency-stop UX tweak per user feedback: `BTN_STOP_WIDTH` shrunk from full-width (312) to a more proportionate size — no longer spans the entire screen.

### Watchdog auto-shutdown has likely never actually worked (found while testing touch's watchdog bypass, not fixed)
- The touch feature added a `touchSessionActive` bypass to `itsbeentoolong()` ([SkiCMD.h](src/SkiCMD.h)) so a touch session isn't killed by the 10s inactivity timeout. Testing that bypass (STOP clears the flag, then wait >10s idle, expect auto-shutdown) showed `shutdown()` never fires **regardless of `touchSessionActive`**.
- Root cause: `main.cpp`'s `loop()` calls `handlePIDControl()` unconditionally every iteration ([main.cpp:172](src/main.cpp#L172)), which calls `handleHEAT(...)` every single time whether or not anything actually changed. `handleHEAT()` unconditionally sets `lastEventTime = micros()` ([SkiCMD.h:98](src/SkiCMD.h#L98)) — the same timestamp `itsbeentoolong()` checks against a 10-second threshold. Since the main loop runs continuously (thousands of times/sec), `lastEventTime` is perpetually refreshed to "now," so `itsbeentoolong()`'s `duration > LAST_EVENT_TIMEOUT` can essentially never be true.
- This predates the touch feature and isn't specific to it — the 10-second auto-shutdown watchdog appears to be dead code for **every** interface (BLE/WiFi/USB/touch), not just touch. Same category as the priority-order bug above: inherited from the fork, flagging rather than fixing per current direction.

### Roaster RX/TX ported to RMT hardware, verified on real hardware

## 2026-08-12

### CHAN's empty Rx root-caused to timing, not the missing-reply bug fixed yesterday
- Yesterday's fix (USB now replies to `CHAN` at all, via `Serial.println` instead of `D_println`) wasn't enough on its own — re-tested with the real Artisan app and `Rx` was still empty every time, while `READ` kept working. Read Artisan's actual source (`artisanlib/comm.py`'s `ARDUINOTC4temperature()`) instead of guessing: it writes `CHAN;...`, sleeps **only 100ms**, then reads a line; if the result is empty (not merely wrong, just *empty*), no exception is raised but `ArduinoIsInitialized` never gets set, so Artisan silently retries the entire CHAN handshake forever (matches the observed ~2s retry loop exactly). `READ` never "fails" the same way because Artisan has no equivalent validation gating on it — a late/empty reply there just becomes `-1` placeholder data.
- Also found two smaller protocol gaps while reading `comm.py`, not yet fixed: Artisan sends `FILT;<filters>` right after CHAN/UNITS during init (to configure per-channel smoothing) and `PID;CHAN;<source>` (from Artisan's own internal software-PID feature) — neither is handled in [SkiCMD.h](src/SkiCMD.h)'s `parseAndExecuteCommands()`. Both are silently ignored rather than breaking anything (empty replies don't fail Artisan's init check), so low priority, but worth doing if a "full TC4 compliance" pass ever happens.

### Root cause of the 100ms miss: USB serial was polled from the display-refresh loop
- Mapped every task's per-iteration cost. `loop()` (roaster RX/TX/PID/state-queue) is dominated by the RMT TX call's ~78ms blocking wait (`rmt_tx_wait_all_done`, unconditional every iteration → ~12.8Hz) but doesn't touch USB. `webSerialLoop()` (the FreeRTOS task from `xTaskCreate`, no core pinned) is where `serialLoop()` lived, gated behind a **fixed `delay(250)`** that traces back to the project's very first commit (`8bd83b3`, originally `delay(500)`, halved in `4ddff16` for unrelated command-queue work) — it was sized to pace the OLED/TFT status redraw, not USB responsiveness; USB got bolted onto the same loop by coincidence of code organization, not design.
- Cross-checked BLE (`ble.cpp`'s `onWrite`) and WebSocket (`CommandLoop.cpp`'s `onWsEvent`): both already reply synchronously from their own stack's callback (NimBLE's / AsyncTCP's background task), completely independent of `webSerialLoop()`'s 250ms cadence — `bleLoop()`/`webSocketLoop()` only refresh the outgoing-reply state snapshot and do connection housekeeping, they don't receive data. USB serial was the only one of the three still polled once per 250ms+ cycle.

### Tried making USB serial event-driven to match BLE/WebSocket — `Serial.onReceive()` doesn't fire on this toolchain
- First attempt: `Serial.onReceive(onSerialReceive)` calling `handleSerialCommand()` (String parsing + `Serial.println()`) directly in the callback. Broke serial entirely after the first command — traced to the callback running in HardwareSerial's own `uart_event_task`, which gets only a **2KB stack** at the **system's highest FreeRTOS priority** (`configMAX_PRIORITIES - 1`); String-heavy work + `Serial.println()` there is a known-bad combination.
- Second attempt: kept the callback minimal (drain bytes into a line, hand off via `xQueueSend` to a proper task). Still completely broken — confirmed via a WebSerial-tail script (decodes the `WebSerial` library's binary frame format directly over its `/wserial` websocket, since the JS client wasn't accessible headlessly) that `onSerialReceive()` **never fires at all**, with or without anything in it. Cross-referenced against `espressif/arduino-esp32` GitHub issues: `onReceive()` has known problems on ESP32/S2 without the UART clock source set to APB; this build (pioarduino platform, `framework-arduinoespressif32-libs @ 5.5.5`) apparently has the same class of issue on S3. Not worth debugging further into the framework — abandoned event-driven Serial for now.
- **Landed on**: a dedicated FreeRTOS task (`serialCommandTask` in [main.cpp](src/main.cpp)) polling `Serial.available()` every 5ms via `vTaskDelay`, completely decoupled from `webSerialLoop()`'s `delay(250)`. Same read/reply logic as before (`handleSerialCommand()`, factored out so both the old removed `serialLoop()` and this task share it), just on its own fast, independent cadence. Verified via raw serial round-trip (bypassing Artisan): `CHAN` now replies in 4-225ms (previously an unconditional ~250-260ms floor that always lost to Artisan's 100ms budget).
- **Verified against the real Artisan app**: `CHAN;1234` now gets `Rx = # Active channels set to 2100` on the very first try (~100ms after port open), no more endless retry loop. `OT1`/`OT2`/`DRUM` control commands confirmed reflected in subsequent `READ` replies (`90,40` etc.) — full USB/TC4 control loop working end-to-end through Artisan.

### Display drawing also split out of webSerialLoop() into its own task
- Once USB was carved out, realized display drawing was *also* only sharing `webSerialLoop()`'s `delay(250)` by coincidence — same "bolted onto whatever loop already had a delay" pattern, dating back to the same day-one commit. Nothing else left in that loop (`WebSerial.loop()`, `ledControl()`, `webSocketLoop()`/`bleLoop()`) actually needs 250ms pacing: `WebSerial.loop()` is designed for tight-loop calling, `ledControl()` already self-paces off its own `millis()` check, and the WebSocket/BLE tick just refreshes a state snapshot (more frequent = fresher, not a problem).
- Split into a new `displayLoop` task ([main.cpp](src/main.cpp)) that owns the `delay(250)` display-refresh rhythm by itself. `webSerialLoop()`'s own delay dropped to `vTaskDelay(1)` — a minimal scheduler yield, not a pacing mechanism (needed so the task doesn't starve the watchdog, not because anything left in it needs spacing out).

### New finding while testing: ESP-IDF's own error log bleeds into the USB TC4 byte stream
- Raw serial capture during testing caught framework log lines interleaved into TC4 replies: `# Active channels set to 2100\r\n\r\n[ 62098][E][AsyncWebSocket.cpp:436] _queueMessage(): Too ...`. ESP-IDF's `log_e()` (here triggered by `AsyncWebSocket`'s send-queue-full warning) defaults to printing to UART0 — the same physical wire Artisan reads TC4 responses from. Whenever that warning fires (e.g. WebSocket client queue backs up), it corrupts whatever Artisan is trying to parse on USB at that moment. **Not fixed yet** — flagged as the next thing to look at (options: redirect ESP-IDF's default log output away from UART0, or lower the log level so this class of warning doesn't print at all).

### ROR recalculated to match Artisan's own algorithm instead of a home-grown one
- The original ROR ([SkiComms.h](src/SkiComms.h)'s `updateROR()`, from the 2026-08-01 dashboard work) averaged a bunch of noisy instantaneous point-to-point slopes over a 5s trailing window -- looked jumpy and didn't read like what Artisan itself would plot from the same temperature stream. User wanted the two to look similar, so read Artisan's actual source (`artisanlib/canvas.py`'s `compute_ror_simple()`) instead of guessing at a design.
- Artisan's real algorithm (confirmed against this project's own `skywalker.aset`, which has `polyfitRoRcalc=false` -- the simple version, not the least-squares polyfit alternative -- and `DeltaSpan=20`/`DeltaETspan=20`): **one slope** between the current reading and a reading ~20 seconds ago, where the *old* end of that slope is locally smoothed (average of nearby samples) but the *current* end is left raw -- smooths noise without adding lag to the newest reading.
- Reimplemented to match: `ROR_SPAN_MS=20000` (from `DeltaSpan`), `ROR_LEFT_SMOOTH_MS=2000` window for the old-end averaging (Artisan does this as a fixed 5-sample average at its own ~2s polling rate from `Delay=2000` in the .aset; since Trident samples much faster via RMT (~114ms), the equivalent is expressed as a time window rather than copying "5 samples" literally -- otherwise it'd smooth over a much narrower real-time span than Artisan's version does). History buffer grew from 20 slots (~2.3s, not even really covering the *old* 5s window it claimed to) to 256 (comfortably covers 20s+ at the RMT sample rate); costs ~3.7KB more RAM, trivial on the S3.
- Known behavior change: ROR now needs a full 20s of history before it shows anything (stays at its last value/0 until then) -- correct per Artisan's own behavior, just slower to first-show than the old 5s-window version.
- Verified on hardware via WebSerial log: `span` consistently 20.0-20.1s, `35-sample left avg` (matches ±2000ms at ~8.75Hz), values smooth and stable at idle instead of jumpy.
